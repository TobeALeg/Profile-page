## 已确认的经历

GEO 是公司要求做的项目。最开始用 Claude Code 开发，是无头的，没有图形界面，先确认业务流程能跑通。

2026-10-08 本人补充：最初最在意的是所有内容一定要基于事实。事实基础依赖客户提供的资料，以及客户对自己的认知；本人明确提到产品认知和客户认知。不把这一原则写成已经核实所有资料绝对准确的成果。

后来花了很长时间搞清楚“我们内容的客户”，也就是做 GEO 是为了什么。在这个过程中形成了方法论。这里还涉及商业问题：如何收费；场景包用于回答这个问题，也用于说明每发一篇内容到底服务什么、会对客户产生什么影响。

本人将这条思考主线放在界面工作之前：先事实约束，再明确内容的客户与目的、形成方法论和场景包，后来才开始做界面。具体方法论版本及各环节日期尚未指定，不把已查到的界面提交日期重新移动，也不把 8 月的 V5/V6 版本直接视为方法论最初形成的日期。

后来需要向客户证明我们有这个产品，拿出去介绍，才用 Codex 做界面。界面不是一次补齐的，而是一点一点做起来的。

再后来，真正需要用它进行 GEO 的规划、管理和发布。mentti、Probe、Post 等工具以及插件，都是在这个过程中逐渐产生的。这是一点一点自动化的过程。

工具切换、开发动机、事实原则及场景包的商业作用来自本人叙述；提交记录只支持功能与代码时间，不据此反推工具或动机。

## 时间线文案草稿

### 先让内容有事实，再让每篇内容有目的

公司要求做 GEO 时，我先用 Claude Code 搭了一套没有图形界面的流程。最开始，我最在意的是：所有内容都要基于事实。这依赖客户提供的资料，也依赖他们对自己的产品和客户的认知。

后来，我花了很长时间去搞清楚，我们的内容究竟服务谁，做 GEO 到底是为了什么。方法论是在这个过程中逐渐形成的。

这也涉及商业上的问题：我们应该如何收费。场景包用来回答这个问题，同时也要说明，每发一篇内容到底在服务什么，以及希望对客户产生什么影响。

在这些思考之后，我们需要拿出去向客户介绍，证明我们有这个产品，我才开始用 Codex 做界面。那时，界面首先承担的是展示和讲解的作用。

再后来，我们真正开始用它做 GEO 的规划、管理和发布。实际工作里的需求不断出现，界面和功能也跟着一点点补齐。mentti、Probe、Post，以及插件，都是在这个过程中逐渐发展出来的。

这段文案按本人叙述串联，尚属编辑草稿；“希望产生的影响”不是已验证的业务效果。收费价格、计费规则和场景包与文章的具体关系尚未展开。

## 编辑提炼：这一段在两条线中的位置

工程线目前最有依据的转折是：从给内容建立事实基础，走向定义内容的服务对象、目的及商业解释，再通过方法论和场景包把这些判断连接到每篇文章。结合已核查的 8 月 CC 对话，可以继续讲系统架构与下游生成如何服务这一方法论；不能从代码反推最初业务动机。

AI / 设计线的后续入口是界面如何表达这些业务判断：客户能否看懂系统依据什么、每篇内容服务什么，以及变化的影响。这里是编辑建议，尚不能把此前所有视觉和审核设计都归因于本轮口述，也不能代写本人当时的设计过程。
